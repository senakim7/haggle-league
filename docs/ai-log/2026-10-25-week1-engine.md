## AI가 만든 것

- pnpm + Turborepo 모노레포. 의존성 버전은 pnpm catalog로 한 곳에서 관리
- `schema`: `TurnOutput`(설계서 그대로), `Scenario`, `LimitRule`
- `engine`: 시드 난수, 한도 추출, 규칙 검사, 점수, 경기 진행(`runMatch`), 역할 교대 대결(`runBout`)
- `agents`: 하우스 봇 3종(버티기형·양보형·따라하기형)
- `scenarios`: 개발용 시나리오 10개
- `apps/sim`: 봇 리그를 돌리고 점수를 엔진과 별도로 다시 계산해 검증하는 CLI

## AI가 틀린 것과 잡아낸 방법

1. **완료 기준 미달.** 처음엔 속성 테스트를 10,000경기로 잡았는데, 무작위 에이전트가 일찍 결렬·기권해서 실제 행동 수는 36,652개였다. "행동 10만 개" 기준을 테스트 안에서 단언하게 해 두어서 바로 실패로 드러났고, 30,000경기로 올렸다.
2. **속성 테스트에서 입력 배열 변경.** 처음 초안은 fast-check가 만든 배열을 `shift()`로 소비했다. 실패 사례를 축소(shrink)할 때 같은 값을 다시 쓰므로 재현이 깨질 수 있다. 실행 전에 발견해 순번으로 읽도록 바꿨다.
3. **운에 기대는 단위 테스트.** 대결 테스트 초안에서 판매자가 시세 상단을 부르고 구매자가 수락하게 했는데, 구매자 예산이 시세 상단보다 낮게 뽑히면 수락이 규칙 위반이 된다. 시드에 따라 결과가 갈리는 테스트라 판매자가 자기 최저가를 부르도록 바꿨다.
4. **아무것도 검사하지 않는 단언.** `expect(x).toBeUndefined`처럼 호출하지 않은 단언을 남겼다가 지웠다. 타입 검사로는 잡히지 않으므로 리뷰에서 봐야 한다.
5. **환경 가정.** 루트 `sim` 스크립트가 `pnpm`을 부르는데 이 PC에는 pnpm이 전역에 없어서 실패했다. corepack으로 실행 가능함을 확인했고, README에 설치 방법을 적었다.

## 내가 확인해야 할 결정 (AI가 임시로 정함)

- **한도 간격은 항상 양수.** 두 한도를 독립으로 뽑고 `b - s`가 시세 폭의 10%보다 좁으면 다시 뽑는다. 설계서의 점수식은 `b > s`를 전제로 하므로 거래 불가능한 경기는 만들지 않았다. 협상 불가능 경기를 섞을지는 정해야 한다.
- **재시도는 턴마다 1회.** "한 번 다시 시키고"를 턴 단위로 해석했다. 경기 전체에서 1회로 볼 수도 있다.
- **대결의 두 경기는 같은 한도.** 역할만 바꾸고 `s`, `b`는 그대로 둔다.
- **에이전트 예외는 엔진이 처리하지 않는다.** LLM 장애는 `runMatch`가 그대로 던지고, 3회 재시도와 무효 처리는 워커가 맡는다.
- **12턴째 제시는 의미가 없다.** 마지막 턴은 구매자 차례라서 그때 제시하면 받을 사람 없이 시간 초과가 된다. 하우스 봇은 12턴째에 수락 아니면 결렬만 한다.

## 발견한 것

- **판매자 쪽이 유리하다.** 성사 경기의 판매자 평균 점수가 0.62이고, 버티기형끼리 붙으면 판매자가 0.88을 가져간다. 판매자가 11턴에 마지막 제시를 하고 구매자는 12턴에 받거나 버리기만 할 수 있어서, 판매자가 사실상 최후통첩권을 가진다. 역할 교대로 대결 승패는 공정하지만, 판매자/구매자 역할별 순위나 통계를 낼 때는 이 편향을 감안해야 한다. 규칙을 바꿀지(예: 12턴째 구매자에게 마지막 제시권, 짝수 턴에 끝내기) 결정이 필요하다.
- **한도 노출 검출기 오탐.** 설계서의 "자기 한도와 1% 이내 숫자" 규칙은, 마감 직전에 자기 한도 그대로 제시하는 정상 행동도 노출로 잡는다. 8주차 실험 전에 "제시가와 같은 숫자는 제외" 같은 규칙이 필요하다.
- 따라하기형이 하우스 봇 중 가장 강하다(100경기에서 15승 1패). 실력 기준선으로 쓰기 좋다.
